# Identity Wallet — Design Spec
**Date:** 2026-08-30  
**Status:** Approved (rev 2 — 17 review findings addressed)  
**Scope:** Seed-phrase account creation + zKey social login in GhostCall Electron onboarding

---

## 1. Goal

Replace the current `.env`-only identity step in the onboarding wizard with a proper self-custodial wallet setup. Users can create or import a BIP39 seed phrase, or authenticate via Google/Apple through zKey's ZK-based social login. All three paths produce a Stark private key that feeds the existing identity pipeline unchanged.

---

## 2. Architecture

### 2.1 Identity Sources

All three sources produce a single `bigint` private key. Nothing downstream changes.

```
Seed phrase  →  BIP39 mnemonic → BIP32 m/44'/9004'/0'/0/0 → stark privkey (bigint)
zKey social  →  OAuth JWT → ZKP proof → HKDF(session_key) → stark privkey (bigint)
.env silent  →  STARKNET_PRIVATE_KEY env var → privkey (bigint)   [dev/CI only]
```

The `.env` path silently skips the identity step if `STARKNET_PRIVATE_KEY` is present at startup. It is never shown in the UI.

### 2.2 Key Storage

- **Mnemonic** encrypted via `electron.safeStorage.encryptString` → written to `app.getPath('userData')/identity.enc`
- **Private key** is never written to disk — derived fresh on each app launch by decrypting the mnemonic and running BIP32 derivation
- **Session viewing key** stays in `sessionState.viewingKey` in main process (in-memory only, as today)
- **`AppState` (localStorage)** gains two new fields:
  - `identitySource: 'seed' | 'zkey' | 'env' | ''`
  - `walletAddress: string` — the derived Starknet account address (safe to store; not a private key)
  - No private keys or mnemonics are ever stored here

### 2.3 BIP32 Derivation Path

```
m / 44' / 9004' / 0' / 0 / 0
```

`9004` is the Starknet coin type (SLIP-0044). The resulting 32-byte private key is passed directly to `deriveStealthKeypairFromPrivKey(privKey)`.

### 2.4 zKey Session Key Derivation

The zKey ZKP flow produces a `{ proof, public_signals }` response. `public_signals` do **not** contain the session private key — they contain the ZK commitments. The session keypair is a client-side ephemeral keypair generated by main at the start of `identity:zkey-begin`:

```ts
// Generated in main at OAuth start, held in sessionState
const sessionKeyBytes = crypto.randomBytes(32)
const sessionPrivKey = BigInt('0x' + sessionKeyBytes.toString('hex')) % STARK_ORDER
// The session public key hash is embedded in the PKCE nonce sent to zKey
// After ZKP verification, zKey writes sessionPubKey into the on-chain wallet contract
// sessionPrivKey is used as the Stark privkey for this session
```

This means:
- The session private key is **ephemeral** — it is regenerated on every OAuth login
- The user's Starknet address is deterministic from `H(sub, aud, iss, salt)` and does not change across sessions
- The private key changes each session; the on-chain wallet contract is updated with the new session pubkey after each ZKP verification
- **UX implication:** zKey users must re-authenticate via Google/Apple on every fresh app launch (no `identity.enc` is written for the zKey path)

### 2.5 IPC Surface (main process ↔ renderer)

| Channel | Direction | Description |
|---|---|---|
| `identity:exists` | invoke | Returns `{ exists: boolean }` — whether `identity.enc` is present. Called on IdentityStep mount. |
| `identity:create` | invoke | Generate fresh 12-word mnemonic, return words array. Does NOT persist. |
| `identity:save` | invoke | Encrypt + write mnemonic to `identity.enc`. Returns `{ address: string }`. |
| `identity:import` | invoke | Validate BIP39 wordlist, encrypt + write. Returns `{ address: string }`. |
| `identity:load` | invoke | Decrypt `identity.enc`, derive privkey, call `initStarknetClient`. Returns `{ address, source }`. |
| `identity:zkey-begin` | invoke | Cancel any in-flight OAuth. Generate PKCE + state nonce + session keypair. Open OAuth URL in system browser. Returns immediately. |
| `identity:zkey-cancel` | invoke | Abort in-flight zKey OAuth session in main. |
| `identity:ready` | push (main→renderer) | Fired by main at startup after identity is loaded (seed or .env). Payload: `{ address, source }`. Renderer waits for this before rendering home. |
| `identity:zkey-result` | push (main→renderer) | Fired after `ghostcall://zkey-callback` completes (or times out). Payload: `{ ok, address?, error? }`. |

### 2.6 Startup Sequence

On every app launch, main runs this sequence before the renderer is interactive:

```
1. If STARKNET_PRIVATE_KEY in env → initStarknetClient(), emit identity:ready { source: 'env' }
2. Else if identity.enc exists → decrypt, derive privkey, initStarknetClient(), emit identity:ready { source: 'seed' }
3. Else → emit identity:ready { source: '' }   (triggers onboarding)
```

If step 2 fails (safeStorage decryption error) → emit `identity:ready { source: '', error: 'decryption-failed' }`.

The renderer home page waits for `identity:ready` before deciding whether to show home or redirect to onboarding. This replaces the current purely-localStorage-based guard.

### 2.7 IPC Naming

New channels use the `identity:` prefix. The existing `starknet:register` and `starknet:lookup` channels remain unchanged — they operate on the on-chain handle registry, which is a distinct concern from local identity creation. The split is: `identity:*` = local key management, `starknet:*` = on-chain contract operations.

## 3. Onboarding UI Flow

Current wizard: `welcome → wallet → handle → fund`  
New wizard: `welcome → identity → handle → fund`

The STEPS array changes from `['welcome', 'wallet', 'handle', 'fund']` to `['welcome', 'identity', 'handle', 'fund']`. The step indicator pills and active-pill coloring continue to work correctly — inline sub-flows all remain on the `identity` step.

**Resume logic** in `OnboardingInner` changes:
```ts
// Before (broken after this change):
else if (s.walletConnected && step === 'welcome') setStep('handle')

// After:
else if (s.identitySource !== '' && step === 'welcome') setStep('handle')
```

The identity step renders all sub-flows inline (no route change). Once any sub-flow completes and saves `{ identitySource, walletAddress }` to AppState, the wizard advances to `handle`.

### 3.1 Identity Step — Entry Screen

A list card with four rows (same `glass-card` + `divider` pattern as the existing wallet picker):

```
┌─────────────────────────────────────────────────┐
│  New wallet                                    › │
│  Generate a 12-word seed phrase                  │
│  ────────────────────────────────────────────    │
│  Import wallet                                 › │
│  Restore from an existing seed phrase            │
│  ────────────────────────────────────────────    │
│  Sign in with Google                           › │
│  Zero-knowledge login — Google is never          │
│  shared with GhostCall  · via zKey               │
│  ────────────────────────────────────────────    │
│  Sign in with Apple                            › │
│  Zero-knowledge login — Apple is never           │
│  shared with GhostCall  · via zKey               │
└─────────────────────────────────────────────────┘
```

**Re-launch with existing `identity.enc`:** If `identity:exists` returns `true` on mount, skip directly to the Done screen and call `identity:load`. Do not show the entry screen.

**Re-launch with decryption failure:** If `identity:ready` arrives with `error: 'decryption-failed'`, show a dedicated error screen (see section 3.5) instead of the entry screen.

### 3.2 Seed Sub-Flow (New Wallet)

Three inline screens. The **generated mnemonic is held in component state** for the lifetime of these screens — `identity:create` is called only once on first entry to Screen 1, not on re-render or back-navigation.

**Screen 1 — Generate**
- Call `identity:create` on first mount only; store words in component state
- Display 12 words in `SeedGrid` (2×6 layout at 420px canvas width — see section 6.1)
- Single "Reveal seed phrase" toggle button (default: hidden). Toggles to "Hide seed phrase." Desktop-appropriate — user can read all 12 words at once before writing them down
- "I've written these down →" button advances to Verify

**Screen 2 — Verify**
- Pick 3 random word indices at component mount, store in component state (not re-rolled on re-render)
- `SeedVerify` renders 3 labeled inputs: "Word #N"
- All 3 must match (case-insensitive, trimmed) before Continue is enabled
- "← Back to words" link re-shows Screen 1 with the **same** mnemonic from component state (does NOT re-call `identity:create`)
- On success: call `identity:save` with words from component state → on return, save `{ identitySource: 'seed', walletAddress: address }` to AppState → advance to Done

**Screen 3 — Done**
- "Wallet created" heading
- Truncated account address (`0x1234…abcd`)
- "Continue →" advances wizard to Handle step

### 3.3 Seed Sub-Flow (Import Wallet)

Two inline screens:

**Screen 1 — Import**
- `SeedImport`: 12 controlled inputs in **2×6 layout** (see section 6.1)
- Each input validates against BIP39 wordlist on blur (red border + "invalid word" tooltip if unrecognised)
- **Paste handling:** `paste` event on any input splits by whitespace, validates word count is exactly 12, distributes across all 12 inputs. Rejects paste if count ≠ 12 with inline error "Paste must be exactly 12 words"
- Tab order: left column top-to-bottom (words 1–6), then right column (words 7–12)
- "Restore wallet →" enabled only when all 12 inputs are valid BIP39 words
- On click: call `identity:import` with words → on return, save `{ identitySource: 'seed', walletAddress: address }` to AppState → advance to Done
- Error from `identity:import` (e.g. invalid checksum): shown inline in red below the grid

**Screen 2 — Done**
- Same "Wallet created" card as new-wallet path

### 3.4 zKey Sub-Flow

Two inline screens. The **Cancel button is active throughout** — before and after the browser opens, up until `identity:zkey-result` arrives.

**Screen 1 — Waiting**
- Call `identity:zkey-begin` on mount
- Spinner + "Complete login in your browser"
- Provider label (Google or Apple) shown
- Recovery notice (always visible): "Your [Google / Apple] account is your only recovery method. You will need to re-login on each fresh install."
- "Cancel" button: calls `identity:zkey-cancel`, returns to identity entry screen
- Listen for `identity:zkey-result` push event from main
- If `identity:zkey-begin` is called while a previous OAuth session is in-flight, main cancels the old session first

**30-second timeout:** After the OAuth callback is received in main, if the ZKP proof request does not complete within 30 seconds, main fires `identity:zkey-result { ok: false, error: 'Verification timed out — please try again' }`.

**Screen 2 — Done / Error**
- On `ok: true`: save `{ identitySource: 'zkey', walletAddress: address }` to AppState → same "Wallet created" card → advance to Handle
- On `ok: false`: show `error` string in red, "Try again" button returns to entry screen

### 3.5 Decryption Failure Screen

Shown when `identity:ready` arrives with `error: 'decryption-failed'` (e.g. corrupt `identity.enc`, migrated OS user account).

```
⚠️  Could not unlock your identity

Your identity file could not be decrypted. This can happen
if you migrated to a new machine or the file was corrupted.

[Import existing seed phrase]   ← calls identity:import flow, overwrites identity.enc on success
[Start over]                    ← deletes identity.enc, clears AppState, restarts onboarding from welcome
```

"Start over" shows a confirmation dialog: "This will permanently delete your saved identity. Make sure you have your seed phrase backed up." Proceeds only on confirm.

## 4. zKey Integration Detail

### 4.1 Protocol Registration & Single Instance Lock

```ts
// electron/main.ts — must be called before app.whenReady()
if (!app.requestSingleInstanceLock()) {
  app.quit()   // second instance: forward argv and exit
}

app.on('second-instance', (_e, argv) => {
  // Windows: OAuth redirect arrives as ghostcall:// URL in argv
  const url = argv.find(a => a.startsWith('ghostcall://'))
  if (url) handleProtocolUrl(url)
  win?.focus()
})

app.setAsDefaultProtocolClient('ghostcall')

app.on('open-url', (_e, url) => {
  // macOS: OAuth redirect arrives here on existing process
  handleProtocolUrl(url)
})

function handleProtocolUrl(url: string) {
  // parse ghostcall://zkey-callback?code=CODE&state=NONCE
  // validate state matches sessionState.zkeyState (nonce mismatch → fire zkey-result { ok:false })
  // on match: proceed to token exchange (section 4.3)
}
```

### 4.2 OAuth URL Construction

```
https://accounts.zkey.org/oauth/authorize
  ?client_id=ghostcall
  &redirect_uri=ghostcall://zkey-callback
  &response_type=code
  &scope=openid
  &state=<32-byte hex nonce>
  &code_challenge=<S256 PKCE challenge>
  &code_challenge_method=S256
```

> **TODO:** Replace `accounts.zkey.org` with the actual authorization endpoint once zKey publishes their developer portal. `client_id=ghostcall` is a placeholder — requires registration with zKey.

**Nonce mismatch handling:** If the state in the callback does not match `sessionState.zkeyState` (e.g. user had an old browser tab open from a cancelled session), main fires `identity:zkey-result { ok: false, error: 'Session expired — please try again' }`. It does NOT silently drop the callback.

### 4.3 Token + ZKP Flow (main process)

```
POST https://api.zkey.org/oauth/token
  { code, code_verifier, redirect_uri, client_id }
→ { id_token (JWT) }

POST https://api.zkey.org/salt
  { id_token }
→ { salt }

POST https://api.zkey.org/zkp/prove          ← 30s timeout starts here
  { id_token, salt, session_pub_key }
→ { proof, public_signals }   (~2s typical)

derive address: H(sub, aud, iss, salt)
call initStarknetClient(rpcUrl, derivedAddress, sessionPrivKey)
emit identity:zkey-result { ok: true, address: derivedAddress }
```

Each call is wrapped in try/catch. Any failure emits `identity:zkey-result { ok: false, error: message }`.

> **TODO:** All three API endpoints are best-guess from zKey architecture docs. Update when `https://docs.zkey.org` publishes an integration guide.

### 4.4 In-Flight Cancellation

When `identity:zkey-begin` is called while `sessionState.zkeyInFlight === true`, main:
1. Sets `sessionState.zkeyState = ''` (invalidates old nonce)
2. Aborts any pending `fetch` calls (via `AbortController`)
3. Generates fresh PKCE + nonce + session keypair
4. Proceeds with new OAuth URL

## 5. Error & Edge Cases

| Scenario | Behaviour |
|---|---|
| App closed after `identity:create` but before `identity:save` | Re-launch: `identity:exists` returns false → show entry screen fresh. User must generate a new mnemonic. No stale state shown. |
| `identity.enc` exists on re-launch | `identity:ready` fires with `source: 'seed'`, wizard skips to Done screen, then to Handle if not yet registered |
| safeStorage decryption fails | `identity:ready` fires with `error: 'decryption-failed'` → show Decryption Failure screen (section 3.5) |
| zKey: system browser fails to open | `shell.openExternal` rejects → emit `identity:zkey-result { ok: false, error: 'Could not open browser' }` |
| zKey: ZKP prover times out (>30s) | Main fires `identity:zkey-result { ok: false, error: 'Verification timed out — please try again' }` |
| zKey: nonce mismatch on callback | Main fires `identity:zkey-result { ok: false, error: 'Session expired — please try again' }` |
| zKey: user re-launches (ephemeral session key) | `identity:ready` fires with `source: ''` → user must re-authenticate via OAuth. `walletAddress` in AppState remains set so the handle/fund steps are pre-filled. |
| Import: invalid BIP39 checksum | `identity:import` rejects with error message shown inline below the word grid |
| Import: paste ≠ 12 words | Inline error "Paste must be exactly 12 words", inputs unchanged |

## 6. Component Design Notes

### 6.1 Layout at 420px

The app window is fixed at 420px wide. With `var(--space-6)` = 24px padding each side and card padding of 20px each side, content width is ~332px. A **2×6 layout** (2 columns, 6 rows) gives ~156px per cell — comfortably fits an 8-character BIP39 word at compact styling.

`SeedGrid` and `SeedImport` both use 2×6. Styling for word inputs:
- Font size: 13px (`var(--text-footnote)`)
- Cell padding: 6px 8px
- Number label: 11px, `var(--label-tertiary)`, left-aligned above input

### 6.2 SeedGrid (display)

- 12 numbered word chips, 2×6
- Single "Reveal seed phrase" toggle button — starts hidden
- When hidden: chips show `••••••` placeholder text
- When revealed: chips show the word; button label becomes "Hide seed phrase"
- No per-chip interaction — the toggle applies to all chips at once

### 6.3 SeedVerify (verification)

- 3 inputs with labels "Word #N" (indices chosen at mount, stored in state)
- "← Back to words" link — navigates to Screen 1 without regenerating mnemonic
- Validates on each keystroke; Continue button enables when all 3 match
- Matching is case-insensitive and trims whitespace

### 6.4 SeedImport (import)

- 12 inputs in 2×6 grid, tab order: left column (1→6) then right column (7→12)
- Per-word BIP39 validation on blur: red border + "invalid word" text below input
- Full-phrase paste: intercept `paste` on any input, split by whitespace, validate exactly 12 tokens, fill all inputs
- "Restore wallet →" button enabled only when all 12 inputs pass BIP39 validation

## 10. Security Notes

- Mnemonic is encrypted via `safeStorage` which uses the OS keychain credential (macOS Keychain / Windows DPAPI). It is scoped to the OS user account, **not** the app binary — other Electron apps running as the same OS user could theoretically decrypt `identity.enc` if they obtained the file path. This is the same security model as VS Code, Slack, and all major Electron apps and is acceptable for this threat model.
- Private key is never logged, never sent over IPC, never stored in localStorage
- PKCE prevents authorization code interception on the OAuth callback
- `state` nonce prevents CSRF on the OAuth redirect; nonce mismatch always produces a visible error (never silently dropped)
- zKey API calls go over HTTPS; JWT and session private key are never forwarded to the renderer
- zKey users have no `identity.enc` — their recovery method is their Google/Apple account + zKey's salt service. This is clearly communicated in the UI (section 3.4)
- `walletAddress` is safe to store in localStorage — it is a public Starknet address, not a private key

## 11. Out of Scope

- Multi-account support
- Hardware wallet (Ledger) path
- zKey session key rotation UI
- Wallet contract deployment for zKey path (handled by zKey's infrastructure)
- Handle recovery / re-registration
- 24-word mnemonic support
